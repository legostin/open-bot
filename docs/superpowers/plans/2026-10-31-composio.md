# Composio Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Slack, GitHub, Google (Gmail, Drive, Docs, Sheets), HubSpot, Dropbox, Box, Discord and any other Composio app
connect through one integration, `integrations/composio`, and everything that goes through it carries a Composio badge
whose note says it is an outside service.

**Architecture:** The core learns two generic abilities: a plugin may have several catalog entries (`integration.entries`
plus entries it reports at runtime with `ctx.catalog.update`), and an integration may go "via" an outside service (a
badge with a note from the plugin's own locales). Sign-in for an entry is delegated to its plugin (`catalog.signin`).
The Composio plugin talks to Composio's REST API v3.1 and registers each connected app's main tools as separate tools,
read-only only when Composio tags them `readOnlyHint`.

**Tech Stack:** Node 24 type-stripped TypeScript, zod, vitest, React + Tailwind (web), SwiftUI (iOS, separate repo
`~/claude-projects/owlbot-ios`).

Spec: `docs/superpowers/specs/2026-10-31-composio-design.md`.

## Global Constraints

- Import local files with `.ts`; only erasable syntax; `import type` for types.
- Every user-facing string in en + ru catalogs (core `packages/core/src/locales`, web `packages/web/src/i18n`,
  plugin `.owlbot-plugin/locales`); text for the model stays English.
- Plugins only `import type` from `@owlbot/plugin-sdk`.
- Tool names match `[a-zA-Z0-9_-]{1,64}`; plugin tools are exposed as `composio_<name>`.
- The Composio key lives only in the vault (`vault://composio`), never in settings or logs.
- Tests write temp files only under `tmpdir()`.

### Task 1: Contracts

**Files:** `packages/shared/src/manifest.ts`, `packages/shared/src/types.ts`, `packages/plugin-sdk/src/types.ts`.

**Produces:**

```ts
// manifest.ts
export const IntegrationViaSchema = z.object({ name: z.string().min(1), about: z.string().min(1), link: z.string().url().optional() });
export const IntegrationEntrySchema = z.object({
  id: z.string().regex(/^[a-z0-9][a-z0-9_-]{0,47}$/),
  name: z.string().min(1),
  summary: z.string().optional(),
  category: z.string().default("other"),
  icon: z.string().default("puzzle"),
  example: z.string().optional(),
  popular: z.number().int().positive().optional(),
});
// IntegrationSchema gains: via: IntegrationViaSchema.optional(), entries: z.array(IntegrationEntrySchema).default([])

// types.ts
export interface IntegrationVia { name: string; about: string; link?: string }
export interface CatalogEntryState {
  id: string;                 // the entry's own id ("slack"), not "<plugin>:<entry>"
  name?: string; summary?: string; category?: string; icon?: string; example?: string; // added entries
  status: "connected" | "needs-setup" | "broken";
  connect: "setup" | "signin";
  account?: string;
  detail?: string;            // plain text or a "%key%" of the plugin's locales
}
// IntegrationView gains: plugin?: string; via?: IntegrationVia; signinReturn?: false

// plugin-sdk types.ts
catalog: {
  update(entries: CatalogEntryState[]): void;
  onSignIn(handler: (entryId: string) => Promise<{ url: string }> | { url: string }): void;
  onSignOut(handler: (entryId: string) => Promise<void> | void): void;
};
tools: { register(tool: ToolRegistration): void; unregister(name: string): void };
```

- [ ] Add the schemas and types; `plainIntegration` in `integrations.ts` returns `entries: []`.
- [ ] `npm run typecheck` passes.

### Task 2: Runner, harness, registry, host

**Files:** `runner.ts`, `plugin-harness.ts`, `registry.ts`, `host.ts`.

**Produces:** requests plugin → core `catalog.update { entries }`, `unregister.tool { name }`; core → plugin
`catalog.signin { entryId } → { url }`, `catalog.signout { entryId }`. Host:
`catalogOf(id): CatalogEntryState[] | undefined`, `catalogSignIn(id, entryId): Promise<string>`,
`catalogSignOut(id, entryId): Promise<void>`, `HostDeps.onCatalogUpdated?(pluginId, before, after)`. Harness:
`catalog: CatalogEntryState[]`, `catalogSignIn(entryId)`, `catalogSignOut(entryId)`.

- [ ] Registry `unregister(name, owner)` deletes only that owner's tool.
- [ ] Host validates reports (plugin must have an `integration` block; at most 200 entries; ids by the entry regex;
  statuses/connect from the allowed sets; strings cut to 200 chars), keeps them per plugin, clears them on stop.
- [ ] Tests in `packages/core/test/catalog-entries.test.ts` drive a fake plugin (written to a temp dir) through the host.

### Task 3: Catalog, API and the agent

**Files:** `integrations.ts`, `app.ts`, `server/api.ts`, `hub-tools.ts`.

- [ ] `entryRef(id)` → `{ pluginId, entryId } | undefined` for `"<plugin>:<entry>"`.
- [ ] `listIntegrations` adds, after a plugin's own card, one view per manifest entry and per reported added entry:
  `id: "<plugin>:<entry>"`, `plugin`, `via` (localized, `{name}` → the entry's name), `signinReturn: false`; status
  `off` while the plugin is off, `broken` when its process fell over, else the reported state (default: `needs-setup`,
  `connect` `setup` while a required setup secret is missing, else `signin`). The plugin's own card gets `via` too.
- [ ] Popular: manifest `entries[].popular`; uses of tools `composio_<entry>_*` count for the entry.
- [ ] `POST /api/integrations/:id/enabled` for an entry turns its plugin on/off; `POST/DELETE /signin` asks the
  plugin; the conversation is remembered and, once the entry is reported `connected`, the agent hears it.
- [ ] `hub_integrations_list` lines say `(through Composio — an outside service)`; descriptions name `composio:<app>`.
- [ ] Core tests for all of it.
